# 27 Oct 2026 — Move the project to SolarFramework
Author: Claude

**Why.** The owner wanted MauLamour built on SolarFramework like their other web apps (MauDonate): framework parent, framework database layer, framework authentication.

**What.** `pom.xml` now inherits `org.solarframework.mu:solar-framework` 1.0 (Java 25, Spring Boot 4.1) and depends on `core`, `database-impl`, `AuthenticationImpl`, `database-editor`, `web-utils`. Removed the old `DatabaseObject`, `AppConfig`, `SecurityConfig`, `AuthController`, `User`, `Email_Verification`, `EmailService`, `IdGenerator`, `Preferences` (its `my.utilities` dependency is gone and nothing used it) and the `accounts/` templates. Every entity is now `@Entity @Table` over `DatabaseObject.ID_OBJ<Long, X>`; views and procedure results (`Profile_View`, `Profile_Edit`, `Chatlist_Item`, `Message_View`, `Message_Reaction_View`) stay plain subclasses read by name. Users are `Account_User`. Login, signup, verification, delete and password reset are `AuthenticationImpl`'s, under `/auth/v1/...`. New: `ViewAdvice` (puts the signed-in account in every page as `me`), a profile-creating interceptor in `WebConfig`, `db/solarframework-migration.sql`.

**How.** `AuthenticationImpl` signs members in by email, so `principal.getName()` is the email; `ChatService` resolves it to the account once, chat queries use user ids, and the typing and call events send the username so the partner never receives an email. STOMP user destinations are addressed by email. The auth module gives every new account a random UUID as its username, so profile and avatar URLs use that. The application class excludes Boot's JDBC/JPA autoconfiguration (a second Hibernate stack otherwise starts and fails; see the DatabaseImpl README). `AuthenticationImpl` always configures `oauth2Login`, so `application.properties` registers Google from `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (placeholders until set). `Profile.getInterests/getLanguages` now read every row (they used `doQuery`, which returned one).

**Checked.** `./mvnw.cmd -o clean compile` with JDK 25 passes. `spring-boot:run` loads component scan, security and controllers and stops at the first database access: MariaDB on port 3309 was not running. Not verified: the SQL migration, every view and procedure, drafts (`Draft.ID` is null on insert, as before, and relies on the column auto-incrementing), signup/login, e-mail sending, chat over STOMP. Source of `AuthenticationImpl` is not in the SolarFramework repository; only a July 2026 jar in `~/.m2` was used.

**Open.** Run the migration on a copy; supply Google credentials; check `MauDonate` still builds (its `AI` dependency has no managed version). `.claude/CLAUDE.md` still says Java 17 / Boot 3.5.5.
